# Guideline Sprint C Report

## Scope

Sprint C adds the Admin Structured Guideline Editor on top of the already-applied Sprint B Guideline Core. It does not rerun or modify `supabase/guideline_core_migration.sql`, does not change Drug, and does not change Calculator formulas or Calculator-Guideline schema.

## Implemented

- Admin Guideline list reads `guideline_documents` through `guidelineRepository`.
- Guideline creation and editing work without a PDF or source URL.
- The editor exposes title, society, condition/specialty, summary, version, publication year, provenance fields, visibility and review notes.
- Lifecycle actions use the existing publication service: draft, in review, publish and archive. Publication blockers are shown from the existing validation policy.
- Section editor supports creation, editing, ordering, archiving and nested parent/child display.
- Section parent changes reject self-parenting, cross-Guideline parents, descendants and existing cycles.
- Recommendation editor uses `guideline_recommendations` independently from `guideline_entries`, supports optional sections, structured evidence/source fields, verification and lifecycle actions.
- Source-document metadata has a separate optional editor. Source documents can be added, edited or removed without making them a prerequisite for a Guideline.
- Unsaved changes show a warning and register a `beforeunload` guard.
- Draft destructive actions and archive actions require confirmation.
- Existing UUIDs are used for every edit; no replacement records are generated by the editor.

## Architecture Decisions

- React components call repository/publication services; the new editor contains no direct Supabase calls.
- `guideline_entries` remains legacy/read-only from this editor and is never converted automatically.
- `guideline_entries.drug_id` is not referenced.
- Source documents are provenance/supporting records, not the Guideline Core itself.
- No migration was executed or rewritten during Sprint C.

## Known Hardening Issues

These are carried forward from the Sprint B migration audit and were intentionally not changed in Sprint C:

1. Legacy `guideline_entries` public exposure still needs a corrective RLS policy audit for archived/non-public parent documents.
2. The Calculator-Guideline public helper still has a legacy visibility/entry compatibility path that needs hardening against the new Guideline Core publication policy.
3. RLS is enabled but `FORCE ROW LEVEL SECURITY` has not been enabled blindly; its service-role implications still require staging verification and an explicit decision.
4. Database lifecycle transition enforcement for `archived -> published` still needs the separate hardening migration/trigger decision.
5. Admin authorization currently uses the established admin-email function; no new editor role was invented.

These issues mean the feature is not a substitute for staging RLS verification.
